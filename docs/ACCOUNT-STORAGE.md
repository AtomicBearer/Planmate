# Accounts, migrations and recovery

This document describes the Node/SQLite host. The separate Netlify adapter uses guest memberships and private Blobs storage; see [NETLIFY-SHARED.md](NETLIFY-SHARED.md). Verified account recovery and the SQLite backup commands below do not apply to that adapter.

Use Node.js 24.13 or newer and `pnpm install --frozen-lockfile`. Runtime dependencies are Google's `google-auth-library` and Sharp; the application remains vanilla HTML/JavaScript with the existing Node server.

## Verified sign-in

Create a Google Identity Services **Web** client and register the exact JavaScript origins where Planmate runs. Put its public client ID in the private `.env` as `GOOGLE_CLIENT_ID`. Start with `node --env-file=.env server.js`. The entry page obtains configuration and a five-minute nonce challenge from the server. Google credentials go directly to the server and are never stored in browser storage. The official library verifies the signature, issuer, audience and expiry; Planmate also checks the nonce and `email_verified`. Accounts use Google's immutable subject, never a local email match. Email is a display/contact field, not a membership proof.

`ACCOUNT_MODE=guest` permits explicitly labelled unverified guest trips while configured Google accounts can create protected account trips. This is the default public release and requires no external API keys. `ACCOUNT_MODE=required` requires verified sessions for new trips and refuses startup without a client ID. Browser-only planning stays on that device. Unconfigured Google sign-in stays hidden; the entry page describes device-profile scope and does not simulate an account. Publish guest mode using [DEPLOYMENT.md](DEPLOYMENT.md); the verified sign-in steps here are optional.

For public use, serve behind HTTPS, set the exact `PUBLIC_ORIGIN` and `SESSION_SECURE=true`, and preserve the incoming Host header. Required mode rejects a non-HTTPS public origin or insecure cookie configuration. Sessions use random identifiers, hashed server storage, HttpOnly/SameSite=Lax cookies, CSRF protection on account mutations, seven-day expiry, rotation at sign-in and current/all-device sign-out. Google account recovery remains with Google. Changing providers, account deletion and retention policy require separate release decisions.

Private profiles live with the account in SQLite. Profile saves compare revisions and retain input on conflict. Reviewing the latest version is explicit. Profile interests are copied to a trip only through **Copy interests & pace from my profile**, followed by **Share my trip preferences**. No email/contact fields appear in shared trip state.

In an account profile, **Copy local travel preferences into this form** offers an explicit import from that browser's local record. It preserves the account display name; review and save separately before it becomes the private account profile. Forms show a loading state until the identity lookup finishes, while return links already preserve the trip context.

## Membership and invitations

Account trips bind a member to an account ID. Opening an already joined trip on another signed-in device finds the same member; joining twice creates no duplicate. Removed accounts cannot rejoin with an invitation. Invitations contain a random key, expire after seven days and can be replaced or revoked by the organizer. Existing members retain access after invitation revocation.

In **Dates & attendance → People & permissions**, the organizer can transfer their role or remove another member. A non-organizer can leave. The organizer must transfer their role first. Former members remain as historical records so comments, suggestions, confirmed versions, uploaded-photo attribution and expense balances survive. Active planning counts and fit rules omit former members. Removal invalidates trip/media authorization and legacy tokens.

Legacy plans import without claiming identities. Sign in on the browser that still holds the original membership token, open the trip, then choose **Bind this legacy membership to my account** and explicitly consent. The server validates both the verified session and the original token at the current trip revision. It retains the member ID/history and revokes that token. A matching email never claims a membership. Lost legacy tokens require a deliberate operator recovery process; there is no automatic email-based recovery. Existing legacy code-only invitations continue in guest mode until the organizer replaces or revokes them; account-required mode needs an invitation generated by the organizer.

## Transactional migration

On startup, `server/storage/plan-store.js` creates `data/plans.sqlite` and applies schema version 1 in a transaction. If `data/plans.json` exists, the server preserves it unchanged, creates `plans.json.pre-sqlite.backup`, validates and imports trips once, and records the import in SQLite. Repeating startup does not overwrite newer trip edits or duplicate records. Invalid source data aborts the import rather than deleting it. Every changed trip revision is compared within `BEGIN IMMEDIATE` before committing. Profile revisions have their own atomic comparison.

This release targets **one Node process on one host with persistent local disk**, using SQLite WAL and a busy timeout. It does not claim horizontally scaled deployment, distributed media storage or multi-instance quotas. Keep the data directory outside publicly served paths. `PLANMATE_DATA_DIR` can point to an absolute data directory; its default is `data/` in the project root.

Planning record feature version 2 adds `endNextDay=false` to older poll options and `needs=[]` to older trip preferences through idempotent defaults. Existing votes, plans, comments, confirmation snapshots, money and media remain intact. Draft input fingerprints now include active membership and candidate metadata; regenerate older drafts before applying them.

## Photos

Own scrapbook media stays in `data/media/<trip-code>/` with generated filenames. Sharp fully decodes JPEG/PNG, rejects unsafe or corrupt images, rotates/re-encodes and omits camera metadata. Limits: 5 MB input/output, 40 megapixels, 12,000 pixels per side, single frame, 40 photos/member, 100 photos/trip, 200 MB/trip and 2 GB/server. Limits are checked again against fresh shared state after processing. A concurrent trip edit rejects the attachment and removes the processed file. Access is checked for each read/write; deleted records revoke reads even if filesystem cleanup fails. Missing-file errors remain visible. Provider photos never enter this storage.

## Offline backup and restore

Stop the server before backing up or restoring so the database snapshot and referenced media belong to the same state. Choose private directories excluded from Git and public serving:

```sh
node scripts/backup.js backup data backups/2026-10-08
node scripts/backup.js restore backups/2026-10-08 recovered-data
```

Backups include a SQLite snapshot, all referenced uploaded photos, accounts/profiles and a checksum manifest. Missing photos fail the backup explicitly. Restore validates checksums, restores into a **new** directory, checks database integrity and invalidates restored sessions/challenges. It never overwrites live data. Set `PLANMATE_DATA_DIR` to the restored directory and restart, then sign in again. Protect backup access like the live database.

For rollback to the pre-migration release, stop the server and use the preserved original JSON and its original media directory in an isolated checkout. That JSON reflects the pre-migration state; later SQLite edits will not appear in it. Prefer a current verified backup for recovery of recent work. Failed/partial backup directories have no valid manifest and should not be used to restore.

## Verification limits

Automated account tests inject identity-verification fixtures at the service boundary. They test nonce/audience/issuer/expiry checks, session invalidation, CSRF, account membership, consent-based claims, revocation, historical balances, private profile revisions, migration/restart and image processing. They **do not verify a real Google sign-in or a deployed HTTPS configuration**. Live validation needs a configured client ID and registered origin; deployment is outside this local implementation.

Primary references: [Google server token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token), [Node SQLite API](https://nodejs.org/api/sqlite.html), [Sharp output and metadata handling](https://sharp.pixelplumbing.com/api-output/).
